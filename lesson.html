Big-O 直觉 + 数组 / Set / Map 怎么选

第 01 节

今晚学什么

审查别人（或自己）的代码时，常出现这类味道：

  • 在长列表上反复 includes / 嵌套循环找人。
  • 明明只是「这个 id 在不在？」却用了最贵的找法。
  • 评论里写了 O(n²)，但说不清「n 是谁、慢在哪一行」。

学完你应能：

  1. 用「大约几步」解释一段循环。
  2. 指出数组 includes 与 Set.has 的差别。
  3. 在「查重 / 按 id 取对象」场景里选数组、Set 或 Map。
和垫课的关系：垫课建立「扫一遍」心智模型；本课把模型接上审查用语（Big-O）和具体 API。
第 02 节

什么叫「慢」——先数步数

先别管符号。假设列表长度是 n，问：这段代码大约执行多少次「看一眼 / 比一下」？

// 例 A：扫一遍
for (const x of list) {
  console.log(x);      // 约 n 次
}

// 例 B：对每个 x，再扫整表找配对
for (const x of list) {
  for (const y of list) {
    /* 比一对 */   // 约 n × n 次
  }
}
具体数字
n = 10 → 例 A 约 10 步，例 B 约 100 步。
n = 1000 → 例 A 约 1000 步，例 B 约 100 万步。差别会「突然」变得很痛。

审查时先定位：哪一层循环？每次循环里有没有又一次完整扫描？

第 03 节

n 与 O(1) / O(n) / O(n²)（口语版）

Big-O 用粗粒度描述「规模变大时，步数怎么涨」。入门够用三个：

写法口语典型样子
O(1) 和 n 几乎无关，固定几步 用下标取 arr[i]；Map/Set 按键查询（平均）
O(n) 和长度成正比，扫一遍 一层 for；arr.includes(x) 最坏
O(n²) 和长度的平方成正比 两层都扫 n；或外层 n 次、每次再 includes 整表
审查话术：「这里对 length=n 的列表做了嵌套扫描，是 O(n²)。n 到几千时可能卡。」——比只丢一个符号更有用。

不必一次学完 O(log n) 等；等你真的碰到二分、平衡树再补即可。

想再看（可选）：任意一本算法入门里「渐近记号」小节；或 MDN 上 Array / Set / Map 方法说明。本页不依赖外链也能学完。

第 04 节

数组：便宜什么、贵什么

数组擅长按位置工作，不擅长反复按内容查找（除非你愿意每次扫）。

操作直觉代价说明
读/写下标 arr[i] O(1) 知道位置就很快
末尾 push / pop 摊还 O(1) 通常很便宜
遍历一遍 O(n) 必然看每个元素
includes / indexOf / find O(n) 最坏从左扫到右
在循环里对每个元素 includes 易变 O(n²) 审查红灯区 
// 贵：对每个 id 都在大数组里 includes
for (const id of incomingIds) {
  if (existingIds.includes(id)) { /* ... */ }
}

若 incomingIds 与 existingIds 都接近 n，总步数可到约 n²。

第 05 节

Set：专门回答「有没有这个值」

Set 存一堆唯一值。平均情况下，has 接近 O(1)——不必每次扫全表。

const existing = new Set(["a", "b", "c"]);
existing.has("b");    // true，查找便宜
existing.add("d");
existing.has("z");    // false

把上面的贵写法改成：

const existingSet = new Set(existingIds); // 先花 O(n) 建好
for (const id of incomingIds) {
  if (existingSet.has(id)) { /* ... */ }     // 每次约 O(1)
}
// 总体约 O(n)，而不是 O(n²)
审查口令：「这里在热路径上对数组 includes；若列表会变长，建议先 new Set 再 has。」

注意：需要顺序、下标、重复元素时，数组仍然合适。Set 不按你插入的「第几个」来取（虽能迭代，但定位模型不同）。

第 06 节

Map：专门回答「这个键对应谁」

Map 存键值对。按键 get / has 平均接近 O(1)。

const byId = new Map([
  ["u1", { id: "u1", name: "阿树" }],
  ["u2", { id: "u2", name: "小陈" }],
]);
byId.get("u2");   // { id: "u2", name: "小陈" }
byId.has("u9");   // false

对比：在对象数组里用 find(u => u.id === id) 是 O(n)。若要查很多次，先建成 Map：

const byId = new Map(users.map(u => [u.id, u]));
// 之后每次 byId.get(id) 都便宜
和普通对象 {}
键几乎总是字符串/数字时，Record<string, T> / 对象字面量也常够用。 Map 更适合键是任意类型、或需要频繁增删且保持插入序等场景。审查里两者都能表达「按 id 索引」。

形状提醒（垫课已见）：{ id: string } 只说明「有个字符串 id」，和用 Map 还是数组无关。

第 07 节

审查场景：怎么选

你想做的事优先考虑别一上来就…
保持顺序、按位置读写、允许重复 数组 强行 Set 丢掉重复与下标语义
很多次「值在不在集合里」 Set（或对象当集合） 循环里 arr.includes
很多次「用 id 取整行数据」 Map / 以 id 为键的对象 每次 arr.find
只扫一次做过滤/映射 数组 filter / map 为一次遍历引入复杂结构
两份列表求交集、查重 先把一侧放进 Set 双重 for 硬比
经验法则：「只处理一次」→ 数组遍历往往够；「同样的查找会做很多次」→ 先建 Set/Map，把之后的查找变便宜。
第 08 节

常见坑（审查清单）

  1. 热路径上的 includes / find
    问：调用频率？列表长度上限？能否预处理成 Set/Map？
  2. 隐藏的 O(n²)
    不一定写成双 for：外层 map，回调里又 filter 全表，同样危险。
  3. 过早优化
    n 永远 < 20 且只跑一次，可读的数组代码可以留。先量规模与频率，再改结构。
  4. Set/Map 建好的成本
    建 Set 是 O(n)。若只查 1 次，includes 一次可能更简单；若查 n 次，建 Set 通常更值。
  5. 用错工具
    需要「第 i 个元素」却用了 Set；需要「去重集合」却反复 push 到数组再手动查重。
